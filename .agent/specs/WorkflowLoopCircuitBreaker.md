# Workflow Loop Circuit Breaker（V4）

> 目的：防止 Agent 在同一个错误上无限重试，同时不引入程序化状态机或预算系统。
> 执行者：Lead 与各角色 Prompt。没有自动熔断器，靠记录与纪律。

## 1. 失败分类

Agent 在动手修复前必须先判断类别，并写进 `findings.md` 或 `handoff.md`：

| 类别 | 典型现象 | 首先应该做的 |
| --- | --- | --- |
| 输入缺失 | 目标不清、验收标准缺失、任务目录不全 | 向 Lead 要事实，不猜测 |
| 环境 | 命令不存在、无网络、无权限、工具不可用 | 记录限制，给替代方案 |
| 设计 | 接口/数据模型无法满足需求 | 回到 Architect 或 Lead |
| 实现 | 编译错误、测试失败、逻辑缺陷 | 定位最小复现 |
| 验证 | 测试不稳定、断言错误、环境不一致 | 区分代码问题与测试问题 |
| 权限/授权 | 需要发布、删除、改历史 | 停下，交 Owner |

## 2. 两次尝试规则

1. 同一条修复路径最多做 **2 次有依据的尝试**。
2. 每次尝试必须满足：
   - 有明确假设（为什么这次会不同）；
   - 有可观察的验证方式（命令 + 预期）；
   - 结果写入记录。
3. 两次失败后**停止该路径**，升级给 Lead。禁止「再试一次看看」。

「有依据」的反例：改随机参数、注释掉测试、加大超时、重跑同一条命令、删除断言。

## 3. 升级路径

```text
角色尝试 1 → 失败 → 记录 → 尝试 2 → 失败 → 升级 Lead
Lead 可自行处理，或改派角色，或调整方案（需记录）
Lead 仍无法解决 → 升级 Owner
```

升级时必须提供：

1. 现象与复现命令；
2. 两次尝试的假设与结果；
3. 你认为的根因（可标注不确定）；
4. 需要对方做的最小动作。

## 4. 必须升级给 Owner 的情形

1. 需要变更范围、目标或验收标准；
2. 需要不可逆操作：强推、改历史、删分支、覆盖 Tag、删除远端资产、正式发布、生产部署；
3. 重大架构取舍（数据模型、协议、安全边界、持久化方案）；
4. 需要额外授权或凭据；
5. 两个角色给出互相矛盾的结论且 Lead 无法裁决；
6. 发现已交付结论建立在错误事实上。

## 5. 必须立即停止（STOP）的情形

1. 发现即将破坏他人工作（未提交修改被覆盖、分支被删）；
2. 发现记录被伪造或与 Git 严重不符；
3. 需要执行未被授权的破坏性命令；
4. 无法判断操作后果，且操作不可逆。

停止时：保留现场，不清理、不 reset、不 stash 丢弃，写入 `handoff.md`，`ACTION: STOP`。

## 6. 记录要求

每次失败与升级，`findings.md` 至少一条：

```markdown
### F<n> <标题>
- Severity: BLOCKER | MAJOR | MINOR
- Status: OPEN | FIXED | WONTFIX(需 Owner 批准)
- Category: 输入 / 环境 / 设计 / 实现 / 验证 / 权限
- Evidence: <命令、输出摘要、文件:行>
- Attempts: 1) <假设与结果> 2) <假设与结果>
- Required fix: <具体动作>
- Resolution: <commit SHA 或 未解决>
```

`WONTFIX` 必须由 Owner 在 `decisions.md` 中批准，否则保持 `OPEN`。

## 7. 反模式

- 用「环境问题」解释所有失败而不提供证据；
- 反复重跑直到偶然通过，然后声称稳定；
- 删除或跳过测试来消除失败；
- 把两次尝试扩成十次，却不改变假设；
- 把需要 Owner 授权的事写成 `ACTION: CONTINUE`。
