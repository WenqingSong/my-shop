# Task: MySQL 与 Redis 依赖接入

## Goal

提供 MySQL 与 Redis 的本地依赖环境（打包在同一个容器内），并让 GoFrame 服务能够建立到两者的连接，服务启动时能够完成连通性校验。

## Scope

允许完成的内容：

- 单一依赖容器定义：MySQL 与 Redis 打包在同一个容器内
- 服务到 MySQL 的连接配置与建立
- 服务到 Redis 的连接配置与建立
- 启动时的连通性校验（连接失败时给出明确反馈）
- 连接信息（主机、端口、账号、密码、库名等）通过配置 / 环境变量注入

## Out of Scope

明确本次不处理：

- 任何业务数据表、模型、迁移
- 缓存业务逻辑（缓存的读写策略等）
- 连接池深度调优、超时/重试策略的精细设计
- MySQL / Redis 的主从、集群、高可用
- 数据一致性 / 缓存一致性设计

## Dependencies

- 依赖 `goframe-scaffold`（需要已建立的工程结构与配置框架）

## Acceptance Criteria

- [ ] AC-001 在全新空白环境中，仅凭仓库内的定义即可启动包含 MySQL 与 Redis 的依赖容器。
- [ ] AC-002 服务启动后能够成功连接 MySQL 与 Redis。
- [ ] AC-003 当 MySQL 或 Redis 不可用或连接失败时，服务给出明确、可识别的错误/日志反馈，而不是静默忽略。
- [ ] AC-004 连接信息（主机、端口、账号、密码等）可通过环境变量配置，代码中不硬编码真实凭据。
- [ ] AC-005 依赖容器的启动与配置可重复执行（环境每日重置后能重新拉起并恢复可用）。

## Relevant Context

- 运行环境为 CNB 云原生开发环境（DinD），环境每日重置：容器关闭、备份卷删除，每次重启都是全新空白环境。因此依赖环境必须由仓库内定义重建，连接配置必须可注入，不能依赖持久化数据。
- MySQL 与 Redis 打包在同一个容器内（按 Owner 要求）。
- 本阶段只验证“能连上”，不涉及业务读写。

Assumption:
- 依赖容器使用仓库内的编排/构建定义（如 docker-compose 或等价方式）重建；具体编排工具由 Coder 结合环境选择，最终以“可重复拉起”为准。

## Verification

建议至少执行：

- 从干净环境拉起依赖容器，确认 MySQL 与 Redis 可用
- 启动服务，确认能够建立到两者的连接（日志/探针可验证）
- 关闭/断开依赖后重启服务，确认能观察到明确的连接失败反馈
