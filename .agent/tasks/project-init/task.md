# Task: 电商项目工程初始化

## Goal

建立一个可编译、可启动的 GoFrame v2 电商项目骨架，接入 MySQL 与 Redis（各自独立容器），提供服务健康检查接口，并完成启动验证。本阶段不实现任何具体业务。

## Scope

允许完成的内容：

- GoFrame v2 工程初始化（模块定义、入口程序、标准目录结构）
- 配置框架：从配置文件读取，并支持环境变量覆盖关键配置
- HTTP 服务启动并监听指定端口
- MySQL 依赖容器（独立容器）
- Redis 依赖容器（独立容器）
- 服务到 MySQL 的连接建立与启动连通性校验
- 服务到 Redis 的连接建立与启动连通性校验
- 健康检查接口（返回服务存活状态）
- 完整启动验证流程

## Out of Scope

明确本次不处理：

- 任何具体业务模块（商品、订单、用户、分类等）
- 数据库表结构、模型、迁移
- 缓存业务逻辑（缓存读写策略等）
- 认证、鉴权及业务中间件
- MySQL / Redis 的主从、集群、高可用
- 数据一致性 / 缓存一致性设计
- 监控指标、告警体系、可观测性平台接入

## Phases

本任务内部按以下顺序完成（严格串行，共同服务于同一个启动验证目标）：

1. Phase 1 — 工程骨架：GoFrame 工程初始化 + 标准目录 + 配置框架，达到可编译、可启动、可监听端口。
2. Phase 2 — 依赖接入：MySQL 与 Redis 各自独立容器，服务建立到两者的连接，启动时完成连通性校验。
3. Phase 3 — 健康检查与验证：health 接口 + 完整启动验证链路。

## Acceptance Criteria

- [ ] AC-001 在全新空白环境中，仅克隆仓库并按说明执行构建命令，工程能成功编译，无缺失依赖或本地特有路径依赖。
- [ ] AC-002 启动服务后，进程正常监听配置指定的 HTTP 端口，不崩溃退出。
- [ ] AC-003 工程目录符合 GoFrame v2 标准目录结构约定，能够直接承载后续业务模块。
- [ ] AC-004 服务配置支持通过环境变量覆盖默认值（如监听端口），无需修改代码即可切换。
- [ ] AC-005 在全新空白环境中，仅凭仓库内定义即可分别启动 MySQL 容器与 Redis 容器，且可重复执行（环境每日重置后能重新拉起）。
- [ ] AC-006 服务启动后能够成功连接 MySQL 与 Redis。
- [ ] AC-007 当 MySQL 或 Redis 不可用或连接失败时，服务给出明确、可识别的错误/日志反馈，而不是静默忽略。
- [ ] AC-008 连接信息（主机、端口、账号、密码等）可通过环境变量配置，代码中不硬编码真实凭据。
- [ ] AC-009 服务启动后，访问健康检查接口返回成功（HTTP 200）及可识别的存活状态。
- [ ] AC-010 从干净环境完整走通链路：拉起依赖容器 → 启动服务 → 服务成功连接 MySQL/Redis → 访问健康接口得到正确结果。

## Relevant Context

- 技术栈：GoFrame v2（Go）。
- 目标是一个电商项目，但本阶段只搭骨架，不实现业务。
- 运行环境为 CNB 云原生开发环境（DinD），环境每日重置：容器关闭、备份卷删除，每次重启都是全新空白环境。因此工程与依赖环境必须由仓库内定义重建、配置必须可注入，不能依赖本地持久化状态。
- MySQL 与 Redis 各自独立容器：一个 MySQL 容器、一个 Redis 容器。

Assumption:
- 采用 GoFrame 官方标准工程结构（api / internal / manifest 分层）。
- 依赖容器使用仓库内的编排/构建定义（如 docker-compose 或等价方式）重建；具体编排工具由 Coder 结合环境选择，最终以“可重复拉起”为准。
- 健康检查接口作为存活探针（liveness），返回服务存活状态；MySQL/Redis 的连通性在服务启动阶段完成校验，不将健康接口扩展为细粒度 readiness 探测。

## Verification

建议至少执行：

- `go build ./...`（或项目规定构建命令）→ 成功
- `go vet ./...` → 无阻塞问题
- 从干净环境拉起依赖容器，确认 MySQL 与 Redis 可用
- 启动服务，确认监听端口正常、启动日志中 MySQL/Redis 连接成功
- 访问健康检查接口，确认返回 200 与健康状态
- 断开依赖后重新启动服务，确认能观察到明确的连接失败反馈
