本任务**不实现业务 API**、不做历史 SQL 导入、不改既有订单状态机与退款流程、不接真实支付渠道、不改
`inventories`/`inventory_logs`/`flash_sale_*`，也不改 OpenAPI/DTO。

## 3. 新增与修改的表结构

### 3.1 `orders`（6 个 additive 列）

| 列 | 类型 | 默认 | 语义 |
| --- | --- | --- | --- |
| `shipping_fee` | INT UNSIGNED | 0 | 运费快照（整数分）；历史订单 0，不重算 `total_amount` |
| `pay_type` | VARCHAR(16) | '' | 支付方式（Mock）；空=未支付/未选择 |
| `transaction_no` | VARCHAR(64) | '' | 支付交易编号（Mock，仅追溯） |
| `delivery_type` | VARCHAR(32) | '' | 物流方式 |
| `delivery_name` | VARCHAR(64) | '' | 物流公司名称 |
| `delivery_sn` | VARCHAR(64) | '' | 物流单号 |

列位置：`shipping_fee` 在 `discount_amount` 之后；`pay_type`/`transaction_no` 在 `user_coupon_id` 之后；
`delivery_*` 在 `refunded_at` 之后。既有列类型与含义未改。

### 3.2 `order_items`

新增 `spec_text VARCHAR(128) NOT NULL DEFAULT ''`（`sku_name` 之后），下单时 SKU 规格文本快照；历史订单为空串，不回填。

### 3.3 `order_status_logs`（新表）

`id`、`order_id`（软引用）、`from_status`、`to_status`、`change_type`、`operator_type`（1=user/2=admin/3=system）、
`operator_id`（默认 0）、`remark`、`created_at`；索引 `idx_order_time(order_id, created_at)`。一单多条、append-only、无 FK。

### 3.4 `wallet_accounts` + `wallet_transactions`（新表）

- `wallet_accounts`：`id`、`user_id`（`uk_user_id` 唯一）、`balance INT UNSIGNED DEFAULT 0`、时间列。
- `wallet_transactions`：`id`、`account_id`（FK→`wallet_accounts` RESTRICT）、`user_id`、`tx_type`、`direction`（1=入账/2=出账）、
  `amount`、`balance_before`、`balance_after`、`biz_type`、`biz_id`（可空）、`idempotency_key`（`uk_idempotency` 唯一）、
  `remark`、`created_at`；索引 `idx_account_id`、`idx_user_id`、`idx_biz`。

### 3.5 `recharge_orders`（新表）

`id`、`order_no`（`uk_order_no`）、`user_id`、`amount`、`status`（默认 10）、`pay_type`（默认 ''）、`paid_at`（可空）、时间列；
索引 `idx_user_status(user_id, status)`。状态：10=待支付、20=支付成功、30=已取消、40=支付失败。

### 3.6 `user_points_accounts` + `user_points_logs`（新表）

- `user_points_accounts`：`id`、`user_id`（`uk_user_id` 唯一）、`points BIGINT UNSIGNED DEFAULT 0`、时间列。
- `user_points_logs`：`id`、`user_id`、`change_amount BIGINT`（带符号）、`points_before/after BIGINT UNSIGNED`、`change_type`、
  `biz_type`、`biz_id`（可空）、`idempotency_key`（`uk_idempotency`）、`remark`、`created_at`；
  索引 `idx_user_time(user_id, created_at)`、`idx_biz`。

### 3.7 `user_coupons`（4 个可空快照列）

`coupon_title VARCHAR(64) NULL`、`coupon_price INT UNSIGNED NULL`、`use_min_price INT UNSIGNED NULL`、`end_time DATETIME NULL`
（均在 `template_id` 之后）。NULL = 历史券未快照；不写入、不回填、不伪造。

## 5. 金额单位及公式

| 项 | 结论 |
| --- | --- |
| 单位 | **整数分**（1 元 = 100 分）；DB `INT UNSIGNED`（余额/积分另有约定），Go `int64`，无 `decimal`/浮点 |
| 商品金额 | `original_amount = Σ(order_items.price × quantity)`，`price` 为下单时重读的 `skus.price` 快照 |
| 优惠券 | `discount_amount = min(模板固定减免, original_amount)`，仅固定金额满减、不叠加 |
| 运费 | `shipping_fee`（新增，默认 0）；当前未实现运费计算 |
| 当前应付 | `total_amount = original_amount - discount_amount`（因 `shipping_fee=0`） |
| 目标应付 | `original - discount - member_discount - points_discount + shipping_fee`（会员/积分/运费均 Deferred，见 `pricing.md`） |
| 舍入 | 当前无比例计算、无舍入；比例折扣/积分换算的取整规则未定（Deferred） |
| 退款 | 整单全额 `= orders.total_amount`（V1，服务端派生） |

历史订单不重算 `total_amount`；`shipping_fee` 只加列、不回填、不改写历史金额。

## 6. 钱包、积分、充值的关键不变量

| 编号 | 不变量 | DB 保证 |
| --- | --- | --- |
| INV-W01 | 一个用户至多一个钱包账户 | `wallet_accounts.uk_user_id` |
| INV-W02 | 余额不得为负 | `balance INT UNSIGNED` + 业务条件更新（`WHERE balance >= ?`） |
| INV-W03 | 每次余额变更可逐笔追溯、只追加 | `direction`/`amount`/`balance_before`/`balance_after`；无 UPDATE/DELETE 路径 |
| INV-W04 | 同一业务请求不重复入账 | `wallet_transactions.uk_idempotency` |
| INV-W05 | 余额变更与流水同事务 | 应用事务（本任务不写业务代码） |
| INV-W06 | 钱包账户不存在时资金操作失败而非静默忽略 | FK `account_id` → `wallet_accounts`（1452） |
| INV-W07 | 同一充值单不重复入账 | 确定性幂等键 `recharge:<id>` + 唯一索引；充值单号 `uk_order_no` |
| INV-M01 | 一个用户至多一个积分账户 | `user_points_accounts.uk_user_id` |
| INV-M02 | 积分不得为负 | `points BIGINT UNSIGNED` + 条件更新 |
| INV-M03 | 每次积分变动可追溯 | `change_amount` + `points_before/after`；append-only |
| INV-M04 | 同一业务事件不重复加减积分 | `user_points_logs.uk_idempotency` |
| INV-M05 | 积分余额与流水同事务 | 应用事务 |
| INV-C11 | 领取后权益快照不被模板修改影响 | 四个快照列；NULL=历史券回退模板 |

## 7. 历史数据兼容策略

| 对象 | 策略 |
| --- | --- |
| `orders` 金额 | 不重算；`shipping_fee` 默认 0；`pay_type`/`transaction_no`/`delivery_*` 默认空串；不推断历史渠道/运单号 |
| `order_items.spec_text` | 默认空串，不回填（历史 `sku_name` 已含规格文本） |
| 历史订单状态 | 不新增 `order_status_logs` 历史行；状态流水写入从 B1-04 起按新事件记录 |
| `wallet_*` / `recharge_orders` / `user_points_*` | 新表为空，不回填、不导入历史资金/积分 |
| `user_coupons` 快照 | 四列 NULL，不回填；读取方回退模板当前值，行为与迁移前一致 |
| 既有券核销 | 预占/核销/释放逻辑未改；新列不参与状态机 |

## 8. 支付模型决策

**不新增独立 `payments` 表**。证据：当前 `order.Pay` 是「待支付→已支付」的一次性幂等推进，仅更新 `status`/`paid_at`，
没有多次支付尝试、渠道流水号或多渠道对账需求；`pay_type`/`transaction_no`/`paid_at` 足以承载 Mock 支付事实。
若未来出现多次支付尝试/独立对账/渠道回调，需先向 Owner 提交证据与方案，再扩展模型（见 `order.md` §2.5）。
