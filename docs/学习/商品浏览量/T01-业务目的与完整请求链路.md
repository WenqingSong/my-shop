## 2. 先放到整个系统里看

商品浏览量是挂在 **SPU（商品主数据）** 上的一个累计字段，回答「这个商品被看过多少次」。它不是独立服务，而是商品详情这条请求链路里的一步副作用：

```text
GET /products/:id（前台公开，无鉴权）
  → ControllerV1.Detail            (internal/controller/product/product.go)
  → service.Product().Detail       (internal/service/product.go，接口访问器)
  → sProduct.Detail                (internal/logic/product/product.go)
      ① UPDATE products SET view_count = view_count + 1, updated_at = updated_at
          WHERE id = ? AND status = on_shelf       ← 计数发生在这里
      ② load(id, on_shelf)         ← 读回自增后的商品 + 图片
      ③ service.Sku().ListByProduct(id, enabled)   ← 组合 SKU 列表
  → DetailRes{ Product(view_count 已是自增后的最新值), Skus }
```

关键点：计数不是独立接口，而是「看详情」这个动作的伴随写入。整条链路里只有 `sProduct.Detail` 里那一条 UPDATE 在改数据。

## 4. 关键源码

### 4.1 路由契约：`DetailReq` 的 `g.Meta`

```text
Path:      api/product/v1/product.go
Symbol:    DetailReq
Why It Matters: 声明了 HTTP 方法、路径与 `:id` 参数，是「路由 → 结构体」的唯一契约来源
```

```go
// DetailReq 前台商品详情请求（仅 on_shelf 可见）。
type DetailReq struct {
	g.Meta `path:"/products/:id" method:"get" tags:"商品" summary:"前台商品详情（仅上架）"`
	Id     int64 `json:"id" in:"path" v:"required" dc:"商品 id"`
}
```

GoFrame 靠 `g.Meta` 的 `path`/`method` 把 URL 与这个结构体绑定；`:id` 会被解析进 `Id` 字段，`v:"required"` 是参数必填校验。出参在 `DetailRes`：

```go
// DetailRes 前台商品详情响应（组合 SPU 与 SKU，仅返回 enabled SKU）。
type DetailRes struct {
	Product
	Skus []*skuv1.Sku `json:"skus" dc:"SKU 列表（前台仅 enabled）"`
}
```

`DetailRes` 内嵌 `Product`，而 `Product` 里的浏览量字段是：

```go
ViewCount  int64  `json:"view_count" dc:"累计浏览量（只读）"`
```

注意 `dc`（描述）里就写了「只读」——这个字段对外只展示，客户端不能写它。

```text
Path:      internal/cmd/routes_frontend.go

Why It Matters: 证明前台详情接口不经过任何 Auth 中间件，所以公开
```

```go
// 前台公开接口：注册、登录、刷新、分类查询、商品查询（无需 token）。
```

### 4.5 核心：`sProduct.Detail`（Required Evidence）

```text
Path:      internal/logic/product/product.go
Symbol:    sProduct.Detail
Why It Matters: 计数写入、可见性、404 判定、读回最新值，全部在这一段
```

```go
// Detail 前台详情：仅 on_shelf 可见，并组合该商品的 enabled SKU。
// 计数语义：先对 on_shelf 商品原子自增 view_count，用「单条条件 UPDATE + RowsAffected」
// 合并「可见性校验 + 计数 + 404 判定」三合一；0 行 → 商品不存在或非上架（4001/404，无写入）；
// 显式 updated_at = updated_at 规避 ON UPDATE CURRENT_TIMESTAMP 副作用；计数失败 fail-hard（500）。
func (s *sProduct) Detail(ctx context.Context, id int64) (*v1.DetailRes, error) {
	result, err := g.DB().Exec(ctx,
		"UPDATE products SET view_count = view_count + 1, updated_at = updated_at WHERE id = ? AND status = ?",
		id, statusOnShelf,
	)
	if err != nil {
		return nil, codes.Wrap(codes.CodeInternalError, fmt.Errorf("计数商品浏览量: %w", err))
	}
	if affected, _ := result.RowsAffected(); affected == 0 {
		return nil, codes.New(codes.CodeProductNotFound)
	}
	p, err := s.load(ctx, id, true)
	if err != nil {
		return nil, err
	}
	skus, err := service.Sku().ListByProduct(ctx, id, true)
	if err != nil {
		return nil, err
	}
	return &v1.DetailRes{Product: *p, Skus: skus}, nil
}
```

顺序是关键：**先 UPDATE 自增，再 `load` 读回**。`load` 内部只查 `status = on_shelf` 的行并把 `view_count` 映射到 `v1.Product`：

```go
// load 按 id 加载商品（含图片），onlyOnShelf=true 时强制 on_shelf，否则 404。
func (s *sProduct) load(ctx context.Context, id int64, onlyOnShelf bool) (*v1.Product, error) {
	model := g.DB().Model("products").Ctx(ctx).Where("id", id)
	if onlyOnShelf {
		model = model.Where("status", statusOnShelf)
	}
	// ... Scan 后 loadImages，再 toProduct(records[0], images[id])
}
```

`toProduct` 里的映射：

```go
ViewCount: r.ViewCount,
```

所以响应里的 `view_count` 是「UPDATE 之后、SELECT 读回」的值——即自增后的最新值。

## 5. 运行时到底发生了什么

以 `GET /products/123`（该商品 `on_shelf`，当前 `view_count = 10`）为例，一次请求的时序：

```text
1. 客户端 GET /products/123
2. GoFrame 匹配 g.Meta 的 path `/products/:id` → 解析 id=123 → 构造 DetailReq{Id:123}，校验 required 通过
3. ControllerV1.Detail(ctx, req) → service.Product().Detail(ctx, 123)
4. service.Product() 返回已注册的 sProduct（init() 完成注册）
5. sProduct.Detail：
   a. g.DB().Exec: UPDATE products SET view_count = view_count + 1, updated_at = updated_at
      WHERE id = 123 AND status = 1(on_shelf)      → view_count 变为 11，RowsAffected = 1
   b. s.load(123, true): SELECT ... WHERE id = 123 AND status = 1  → 读到 view_count = 11
      + loadImages → toProduct 组装 v1.Product{ ViewCount: 11, ... }
   c. service.Sku().ListByProduct(123, true) → 取 enabled SKU 列表
   d. 返回 DetailRes{ Product(11), Skus }
6. Controller 把 DetailRes 交给 GoFrame 序列化为 JSON，客户端看到 view_count = 11
```

注意第 5a 步：如果 `123` 是 `draft` 或 `off_shelf`，UPDATE 的 `WHERE status = 1` 命不中任何行，`RowsAffected = 0`，直接在第 5a 步就返回 404，**根本不会走到 load**，也不会计数。这是「计数 + 可见性」在一条 SQL 里合并的原因（细节在 T04）。

## 6. 为什么这样设计

### 6.1 为什么「先 UPDATE 计数、再 load」

因为响应要展示「本次浏览后」的最新累计值。如果先 load 再 UPDATE，响应里的 `view_count` 就是自增前的旧值（少了刚发生的这一次）。「先写后读」用多一次查询换来自增后的准确值，对单次详情请求来说是可接受的成本。

### 6.2 为什么计数粒度是 SPU 而不是 SKU

源码事实：计数列 `view_count` 建在 `products` 表（T02），自增语句按 `products.id` 定位，路由是 `GET /products/:id`——三者都是 SPU 粒度。SKU 是同一商品下的规格变体，展示在同一个商品详情页里，不存在「按单个 SKU 进入独立详情页」的入口，所以计数天然落在 SPU 上。

> 推断说明：设计文档 §2.4 只写了「计数粒度为 SPU（products.id）」，没有额外阐述理由。上面「详情页是 SPU 粒度、SKU 无独立详情入口」是从路由与表结构反推的结论，非文档原话。面试时可这样表达，但要知道它属于「从实现反推的合理性」，不是明文规定。

### 6.3 为什么前台无鉴权

前台是面向所有访客的公开商城主页，任何人浏览商品详情都应该可见；因此 `GET /products/:id` 挂在 `routes_frontend.go` 的无 Auth 位置。这里不展开 RBAC（属 OUT_OF_SCOPE），只需要记住：**前台详情公开，后台详情（`/admin/products/:id`）才需要鉴权**。

### 6.4 哪些入口计数、哪些不计数

| 入口 | 是否计数 | 证据 |
|------|----------|------|
| 前台详情 `GET /products/:id` | **计数**（仅 on_shelf 命中） | `sProduct.Detail` 里的 UPDATE |
| 前台列表 `GET /products` | 不计数（只读返回 `view_count`） | `sProduct.List` / `queryList` 只有 SELECT |
| 后台详情 `GET /admin/products/:id` | 不计数 | `sProduct.AdminDetail` 直接 `load`，无 UPDATE |
| 后台列表 `GET /admin/products` | 不计数 | `queryList` 只 SELECT |
| 写接口（Create/Update/OnShelf/OffShelf） | 不计数 | 均无 `view_count` 自增，只返回只读的当前值 |

设计文档 §2.4 总结为一句：「仅前台公开详情 `GET /products/:id` 访问 `on_shelf` 商品时原子自增；前后台列表、后台详情均不触发」。

## 7. 容易混淆的概念

- **前台 `Detail` vs 后台 `AdminDetail`**：两者都返回 `view_count`，但只有前台 `Detail` 会自增。后台看详情（比如运营检查）不应该刷浏览量，否则 `view_count` 会被内部操作污染。区别就在「有没有那句 UPDATE」。
- **列表里的 `view_count` 是快照**：列表只 SELECT，展示的是查询时刻的累计值，不触发自增。别把「列表能看到 view_count」误当成「列表也在计数」。

## 11. Reference Answers

> 以下是判分点与示例答案，不是逐字背诵的标准作文。自测时先自己答，再对照判分点。

### 第 1 题

**Expected Points**：
- Controller：`ControllerV1.Detail`（`internal/controller/product/product.go`）
- Service 访问器：`service.Product()` → `IProduct.Detail`
- Logic：`sProduct.Detail`（`internal/logic/product/product.go`）
- 计数 SQL 在 Logic 层的 `sProduct.Detail` 里（`g.DB().Exec` 那条 UPDATE）

**Example Answer**：请求先到 `ControllerV1.Detail`，它只把 `req.Id` 转发给 `service.Product().Detail`；`service.Product()` 返回已注册的 `sProduct` 实现，进入 `sProduct.Detail`，在这里执行 `UPDATE products SET view_count = view_count + 1 ...` 完成计数，再 `load` 读回、组合 SKU 返回。

### 第 2 题

**Expected Points**：
- 响应值变成「自增前的旧值」
- 原因：先读时 `view_count` 还没 +1，读到的快照不含本次浏览
- 结论：违背「响应展示本次浏览后最新累计值」的意图

**Example Answer**：会返回自增前的旧值。因为 load 在 UPDATE 之前执行，读到的 `view_count` 还没包含当前这次访问，最后响应展示的是少了 1 的值。现有「先写后读」正是为了避免这一点。

### 第 3 题

**Expected Points**：
- `path`/`method` 定义路由契约，让 GoFrame 把 URL 与结构体绑定
- `in:"path"` 表示 `Id` 从 URL 路径的 `:id` 解析而来
- `v:"required"` 是必填校验

**Example Answer**：`g.Meta` 里的 `path:"/products/:id" method:"get"` 是路由与方法的唯一声明，GoFrame 据此匹配请求；`Id` 上的 `in:"path"` 让它从路径参数 `:id` 取值，`v:"required"` 要求该参数必填。

### 第 4 题

**Expected Points**：
- 不会 +1
- 因为 UPDATE 的 `WHERE status = on_shelf` 命不中 off_shelf 行，`RowsAffected = 0`
- 直接返回 404，无写入、无计数

**Example Answer**：不会 +1。计数 UPDATE 带了 `status = on_shelf` 条件，off_shelf 商品命中不到行，`RowsAffected = 0`，代码直接返回 404，计数没发生。

### 第 5 题

**Expected Points**：
- 不会暴涨
- 后台详情走 `sProduct.AdminDetail`，只有 `load`、没有 UPDATE
- 计数只在「前台详情 `Detail`」触发

**Example Answer**：不会。后台详情是 `AdminDetail`，它直接 `load` 查询，没有自增语句；计数只在前台公开详情 `Detail` 里触发，后台反复查看不会刷浏览量。
