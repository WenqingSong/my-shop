## 2. Mastery Goal

完成这次学习后，Owner 应能：

- 不看源码，画出一条 `GET /products/:id` 请求从 HTTP 到 SQL 再到响应的完整链路，并指出每一步所在文件与符号；
- 解释为什么「单条条件 UPDATE `SET view_count = view_count + 1`」在并发下不丢计数，而「SELECT → 内存 +1 → UPDATE」会丢；
- 解释 `updated_at = updated_at` 这一显式写法的真实目的（规避 `ON UPDATE CURRENT_TIMESTAMP` 副作用），以及 `RowsAffected = 0 → 404`、计数失败 fail-hard 500 的失败语义；
- 说出三条真实测试（正常计数 / 404 不写 / 并发不丢）各自证明什么，并能指出关键断言；
- 在面试追问下，说清 V1 的取舍（不去重、同步计数、单 MySQL）与规模升级后的演进方向（Redis、异步、分表）。

## 3. Feature / System Overview

```text
GET /products/:id  (前台公开，无鉴权)
  → ControllerV1.Detail (internal/controller/product/product.go)
  → service.Product().Detail (internal/service 接口)
  → sProduct.Detail (internal/logic/product/product.go)
      ├─ UPDATE products SET view_count = view_count + 1, updated_at = updated_at
      │     WHERE id = ? AND status = on_shelf
      │     ├─ err            → 500 (CodeInternalError, fail-hard)
      │     └─ RowsAffected=0 → 404 (CodeProductNotFound, 无写入)
      ├─ load(id, on_shelf) → 商品 + 图片
      └─ service.Sku().ListByProduct(id, enabled) → SKU 列表
  → DetailRes{ Product(view_count 已自增后的最新值), Skus }
```

核心事实：整个功能本质是**一条条件 UPDATE 语句 + 对其结果的解释**。计数触发仅限前台公开详情访问 `on_shelf` 商品；列表、后台详情、写接口均不计数，但都返回只读的 `view_count`。

## 5. Scope

### IN_SCOPE

- 业务目的：为什么商品需要累计浏览量，计数粒度（SPU）、触发条件（仅前台详情 on_shelf）、展示位置。
- 完整请求链路：HTTP → Controller → Service → Logic → 单条条件 UPDATE → load/SKU → 响应。
- 数据模型：`view_count` 字段类型/默认值、migration、`Product` 结构映射（DB ↔ 内部 struct ↔ API struct）。
- 核心机制：原子自增、并发正确性、`updated_at = updated_at` 语义。
- 失败语义：`RowsAffected`/404、fail-hard 500、计数独立提交。
- 测试证据：三条测试如何证明上述性质。
- Trade-off 与扩展：V1 取舍、高并发下 Redis/异步方案演进。

### JUST_IN_TIME_PREREQUISITE

- SQL 单条 UPDATE 的原子执行语义与 InnoDB 行锁（补到足以解释「为什么不丢计数」，不下钻内核）。
- GoFrame 分层（Controller/Service/Logic）的最小认知（能定位链路即可）。
- golang-migrate 迁移的最小认知（version 编号 + 只执行一次，足以读懂迁移文件注释即可）。

### OUT_OF_SCOPE

- InnoDB 内核原理（MVCC、redo/undo log、buffer pool、B+ Tree、锁类型细节）。
- Redis / MQ / 异步计数方案的落地实现（只在 T06 作为演进方向讨论，不写实现）。
- 商品 SPU 的完整 CRUD、状态机、SKU/库存/订单/秒杀等相邻模块（仅在需要理解详情链路时点到为止）。
- RBAC / 权限体系（该功能前台公开，无鉴权，不展开）。

### T04 — `RowsAffected`/404 与 fail-hard 失败语义

- Goal: 解释这条 UPDATE 的结果如何被解释为 404 / 500，以及「三合一」设计与 fail-hard 语义。
- Depth: L3
- Interview Value: HIGH
- Estimated Time: 25 min
- Depends On: T03
- Output: T04-RowsAffected与404失败语义.md

Source Scope:

- `internal/codes/codes.go` — `CodeProductNotFound`(4001→404) / `CodeInternalError`(1000→500)

Must Answer:
- `RowsAffected == 0` 表示什么？为什么它能同时覆盖「不存在」与「非 on_shelf」两种情况，并统一为 404？

- `RowsAffected`、条件 UPDATE 的幂等/竞态规避、fail-hard、错误码与 HTTP 状态分离。
